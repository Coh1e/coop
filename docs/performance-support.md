# 本地查询与刷新性能

日期：2026-10-27。任务：#19（初版测量与索引）、#23（共用 bucket 刷新）、#44（真实规模下的查询与刷新性能），父规格 #21。本文记录完整进程的测量方法、当前代码在真实根与真实规模输入上的结果、已证实的优化与仍未达成的目标；区分本轮运行、静态检查、历史结果与未运行。所有夹具、缓存、日志都在项目内；真实操作只作用于本机选定的共用 Scoop 根。

## 目标与判定

规格保留的性能目标：`version` 尽量低于 30ms，缓存命中 `list`/本地 `info` 低于 50ms，索引命中 `search` 低于 100ms。这是待验证目标，不是任何机器上的保证。本页逐项报告实际值；超标项不隐藏，也不把局部结果当作所有规模的成绩。

## 方法

- 每个样本测量完整进程启动到退出：`Process.Start` 到 `WaitForExit` 的挂钟时间，包含进程创建、加载、CLI 工作与退出；没有常驻服务、进程内计时或预热缓存填充。
- `tests/perf.ps1`（CTest `performance`）对每个场景执行 7 次，报告首跑 `first_ms` 与后续 `p50`/`p90`/`p95`/`min`/`max`。`p95` 取热样本的最近秩。
- 进程创建地板：同一测量方式运行 `cmd.exe /d /c exit 0`，本轮 p50 为 29.1–42.8ms（多次运行波动）。`coop.exe` 的启动工作必须与这个地板区分。
- 合成数据：Manifest 约 0.6KB，bucket 规模 200/1500/3000（约精选 bucket、Scoop Main、Main+Extras）。安装根 25/100 个包，每第 4 个包另有 2 个旧版本且无 Coop 记录，代表未接管的既有安装。
- bucket 读取分三种路径：未注册目录（扫描）、`bucket add` 注册的本地目录（本地索引）、Git 共享工作树（按已发布 revision 校验索引）。
- `tests/perf-real.ps1` 在真实根 `C:\Users\Neo\scoop` 上测量查询与刷新：`main` 1,701 个 Manifest、`nerd-fonts` 367 个、实际安装 15 个包，`.coop/transactions` 中累计 636 份已结算日志（journal.json 合计 4.4MB，来自此前真实操作）。查询前后核对注册表、索引、工作树 revision 与 `git status` 未变。
- 真实规模的首次/有变化/无变化刷新用真实 `main` 的项目内副本（1,783 个文件、约 64.7MB 对象）经 `file://` 顺序执行，避免额外网络负载；真实网络载荷用 `https://github.com/ScoopInstaller/Main` 的首次（固定到 `89b4cf80…`）与无变化刷新测量。
- 缓存条件按场景标注：查询在索引刚由刷新写好后执行，文件多半已在 OS 缓存；重复首次刷新复用同一上游副本，只有每个系列的首个样本标为首次。Windows 待机列表清理需要管理员权限，本页不宣称系统级冷缓存。
- 一次测量期间观察到构建输出路径上的 `coop.exe` 被环境扫描（同一文件复制到其他路径后 `--version` 从约 100ms 降到约 20ms），相关基线被作废并重新测量；下表的数值均在文件身份稳定后取得。真实机器上的杀毒/索引服务仍会影响单次数值，本页用多次热样本的 p50/p95 而不是单次最小值。
- 环境：Windows 11 专业工作站版 N 10.0.26300 build 26300；AMD Ryzen 7 8845HS（16 逻辑处理器）；64GiB 内存；KIOXIA-EXCERIA G2 NVMe SSD；PowerShell 7.6.5；CMake 4.4.4；Ninja 1.13.2；git 2.56.0.windows.4；Scoop v0.6.0（2026-09-30）；`coop 0.1.0` Release（MSVC `/W4 /WX`），提交 `7a42d60`，`coop.exe` SHA256 `1ec35fa5…`（本轮优化后构建，链接时间 2026-10-27T08:02:19Z）。

## 已实施的优化

### #44

1. **`info`/`search` 按条件过滤，不再先构建整份目录**（`src/query.cpp`）：旧实现先把所有 bucket 的全部条目构造成 JSON 数组再排序、再匹配，单个 `info` 的成本与整桶规模相同。现在边读边匹配，只构造命中条目，排序只作用于命中集；输出字段与顺序不变。3000 规模索引 `info` 的 p50 从 80.8ms（同机优化前采样）降到 49.0ms，索引 `search` 从 67.3ms 降到 48.2ms。
2. **`info` 只读取目标包的安装事实**（`src/query.cpp`）：架构选择只需要一个包的安装记录，旧实现调用完整 `installed_packages`（包含所有已安装包的旧版本清单与事务扫描）。现在直接读该包的安装事实；只有当前链接缺失（未完成事务）时才回退到完整列表，以保留中断场景的既有语义。
3. **未记录的本地旧版本不再计算目录树证据**（`src/versions.cpp`）：`version_tree_stamp` 只在存在 Coop 版本记录、确实要比较记录指纹时计算。Scoop 自己维护的旧版本不是 Coop 的清理候选，旧实现对它们也整棵遍历，真实根上仅 Git 的旧版本就有 38,345 个文件。
4. **`list` 每次运行只扫描一次事务历史**（`src/query.cpp`、`src/versions.cpp`）：旧实现为每个已安装包重新读取 `.coop/transactions` 并解析全部日志，636 份历史日志被读了约 17 遍。现在待恢复报告只生成一次，并复用为旧版本清单的“有未完成事务”保护标志。真实根 `list` 从 2.7s 降到 1.2s。
5. **目录树证据改用一次目录枚举**（`src/versions.cpp`）：`collect_tree_stamp` 原来对每个条目再调用 `GetFileAttributesW`/`GetFileAttributesExW`，相当于每个文件两次系统调用。改为 `FindFirstFileW`/`FindNextFileW`，大小与时间由枚举结果直接得到，reparse point 与目录判定不变，指纹材料格式不变。真实根 `list` 从 1.2s 降到 0.38s。

### 历史（#19、#23）

6. **可重建查询索引**（`src/catalog_index.cpp`）：bucket 显式 `add`/`update` 时把 Manifest 的搜索元数据写入 `.coop/index/<名称>.json`（紧凑 JSON），查询只读，不联网、不隐式刷新、不在查询期间写状态。Git 来源以已发布 `path` + `revision` 校验；本地/未注册来源以 `(文件名, 大小, 修改时间)` 指纹校验。索引不匹配、缺失或损坏时回退到 Manifest 扫描，坏 Manifest 的诊断同样进入索引。
7. **`list` 旧版本证据延迟读取**（`src/versions.cpp`）：当前版本和受保护版本不再在每次查询中读取 Manifest/安装记录/目录树证据。
8. **复用 CNG SHA256 provider**（`src/crypto.cpp`）：每进程只打开一次算法 provider。
9. **共用 bucket 的原地刷新**（#23）：`bucket add` 克隆到 Scoop 共用工作树；`bucket update` 在 `.git` 内 fetch、先校验目标树、再原地检出，并在 revision 变化前使索引失效。
