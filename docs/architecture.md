## 1. 用户得到什么

Coop 是 C++23 / Windows 原生软件包管理器。它直接与用户已有的 Scoop 安装共用安装根、bucket、软件、入口、持久化数据和安装记录，不要求接管或迁移。两个客户端可以先后交替管理同一批软件，但不承诺同时写入。

无需为 Coop 核心预装 Git、7-Zip。Git 操作通过库完成，libgit2 为首选候选；解压实现尚待调查。公开 HTTPS Git 仓库不限于 GitHub；本地 bucket 可使用。私有或 SSH 来源只读本地已有内容，暂不联网同步。

devkit 提供实际使用场景：Git、Neovim、ripgrep、CMake 等工具的获取、入口和生命周期。其配置联接、终端定制、用户环境引导流程不自动成为 Coop 首版功能，也不作为安装 Coop 开发环境的脚本执行。

## 2. 命令行为提案

| 命令 | 用户可观察行为 |
| --- | --- |
| `coop list` | 显示已接管、未接管及无法管理的安装及原因；本地读取，不启动 PowerShell |
| `coop search <query>` / `info <package>` | 查询本地 bucket / 安装记录；不联网刷新，不启动 PowerShell；标明来源与同步时间 |
| ~~`coop adopt [package] --dry-run`~~ | 已退役（R22/#43 移除）：历史原型中的接管预检；现为未知命令（退出码 2），共享安装直接由 `update`/`uninstall` 管理 |
| ~~`coop adopt [package]`~~ | 已退役（R22/#43 移除）：历史原型中的原地接管；不再有接管步骤或私有记录门槛 |
| `coop install <package>` | 使用本地已同步 Manifest，按需联网下载软件产物；不隐式同步 bucket |
| `coop update <package>` / `--all` | 依据本地 Manifest 更新软件；不更新 Coop 自身、不隐式同步 bucket |
| `coop bucket update [name]` | 显式联网刷新允许的来源；显示成功、未变化或失败及本地快照是否仍可用 |
| `coop bucket list/add/remove` | 管理来源；移除 bucket 不等于卸载其软件 |
| `coop uninstall <package>` | 检查反向依赖，卸载软件，默认保留持久化数据 |
| `coop uninstall <package> --purge` | 独立请求删除持久化数据，先列出范围；具体名称和确认方式待 CLI 规格确定 |
| `coop cleanup [package]` | 显式清理不再使用的旧版本；不删除当前版本或作为恢复依据的版本；预览用 `delete_scope`/`keep_scope` 列出准确范围 |
| `coop reset <package>@<version>` | 只从本机已有版本回退程序；不联网、不猜测下载地址、不重跑 Hook/安装器，不承诺数据回退 |
| 修改命令的 `--dry-run` | 展示计划及已知限制，不运行安装脚本、不改变安装或 bucket 状态 |

暂不引入裸 `coop update` 的模糊含义；最终命令命名待 CLI 规格确定。单次预览不保证实际执行必然成功，尤其无法预测任意脚本的外部副作用。

预览以现有本地数据生成；缺失 Manifest、来源信息或必要证据时说明缺口，不在后台同步来补齐。基础命令的标准输出和诊断可分离：标准输出为 UTF-8 结果，标准错误为诊断；批量部分成功必须有逐包结果与非零总体状态。退出码固定为 0（完成）、1（操作失败或批量部分失败）、2（命令行用法错误），路径归一化、长路径、UTF-8 输出、批量与系统级只读细节见 [CLI 路径、退出码与批量边界](cli-boundaries.md)。

## 3. 管理状态与操作状态分开

不能用一个 `installed=true` 表示所有事实。建议分开记录：

| 维度 | 状态与含义 |
| --- | --- |
| 安装事实 | 路径、版本目录、current、保存的 Manifest、持久化数据是否存在；可记录损坏/不一致 |
| 管理资格 | 未接管 / 已接管；有拒绝原因与检查证据，不以目录存在代替资格 |
| 操作状态 | 无操作 / 准备中 / 修改中 / 已提交 / 已恢复 / 需要人工恢复 |

接管预检结果与实际接管分开：预检通过只代表当时具备条件，不写成已接管。包可在更新失败时仍属于已接管，但带有待恢复操作；此时阻止新的写操作，仍允许查询。

Coop 的管理记录至少需要包来源标识、架构、已安装版本、当前版本、原始 Manifest 原文与摘要、检查能力版本、实际路径/链接、已知依赖、入口归属，以及最近操作结果。原始 Scoop 记录保留作为证据，不在迁移时假定其完全正确，也不假定其他工具会理解 Coop 新记录。

逻辑上区分 bucket 来源、安装记录、操作日志、迁移备份和查询索引；首版优先文件/JSON，具体 schema 和磁盘位置尚待规格固定。查询索引可重建，不能成为唯一安装事实来源；日志和备份不可作为可随意清理的缓存。

## 4. 接管流程

1. 读取明确的用户级 Scoop 根目录及本地证据；检测系统级安装但不接管。不运行 Scoop 或 Manifest hook 来探测状态。
2. 识别版本目录、current、安装记录、原始 Manifest、持久化链接、命令入口、环境暴露、依赖和 bucket 来源。路径不一致、链接逃逸、来源不明等按实际检查报告，不猜测修复。
3. 分别检查安装现状、更新/卸载所需能力及所选验证集覆盖；动态脚本不能仅靠静态词法扫描证明完整兼容。未测试与已知不支持分开标记。
4. 生成逐包预览；不符合条件的包继续可查看/运行，不能更新、卸载或作为删除目标。未接管包的已知依赖也纳入删除保护；证据不完整时不能据此宣称不存在依赖。
5. 实际执行前取得写锁并重查输入摘要，保存迁移备份，再提交 Coop 管理记录。接管本身不重跑安装脚本、不搬动软件或持久化数据。
6. 汇报成功、跳过、失败和恢复状态。备份只能恢复它覆盖的记录和操作，不能声称可以撤销随后任意外部脚本改动。

仅有“原地保留路径”不意味着所有包均可安全接管；原安装可能依赖 Scoop 私有函数、旧环境、外部工具或不一致记录，必须逐项检查。未接管包仍占用的入口和数据也不能被新安装覆盖。

## 5. 模块与接口提案

主写路径：**命令 → Scoop Adapter → Package IR → 验证 → Plan → Executor → Windows 实现 / 状态记录**。

查询走只读目录/元数据路径，不要求整个包先通过安装执行验证；必要时对单个 Manifest 显示解析错误。这保证一个不支持安装的包不会从 search/list/info 中消失。

| Module | 小接口应表达什么 | 隐藏的实现 |
| --- | --- | --- |
| 本地目录与安装读取 | 查询包、来源及安装现状，携带诊断 | bucket 布局、Scoop 记录、可重建索引、链接检查 |
| Bucket 仓库 | 检查来源、准备确定修订、发布变更结果 | libgit2、ref/object、代理/TLS、内容差异与恢复 |
| Scoop Adapter | 将具体 Manifest 与架构转换为强类型包描述或诊断 | JSON 形状、架构覆盖、Scoop 字段与脚本语义映射 |
| Planner | 输入目标、包描述与本地事实，输出计划与前置条件 | 依赖顺序、能力判断、路径与入口冲突、恢复要求 |
| Executor | 执行通过重查的计划，返回逐操作结果与恢复状态 | 下载、校验、解压、进程、日志、状态提交和 Windows 操作 |

模块可为同一可执行文件中的普通代码组织，不因此引入动态插件、RPC、后台服务或逐层抽象基类。Git 库对象不泄漏给包执行器；执行器不依赖 Scoop JSON 字段名称。脚本兼容实现可理解 Scoop 上下文，通过明确的脚本操作接入执行器。

### Package IR 的最小信息

- 身份：来源、包名、版本、架构、Manifest 摘要；版本不先假定为 SemVer。
- 产物：有序下载项、校验描述、解压布局、对应关系。
- 依赖：原始来源限定与包身份；只支持实际已调查的语义。
- 生命周期：有明确阶段的声明式安装/卸载行为和脚本描述。
- 对外能力：命令入口、快捷方式、PATH 项、环境变量；包含目标和归属。
- 持久化：路径映射与保留要求。
- 来源证据：供诊断追溯的 Manifest 字段位置和原文引用；不让任意 JSON 继续驱动执行。

Plan 是针对当前本地状态生成的具体操作及依赖顺序，包含检查前提、执行能力、预期改动、补偿或人工恢复说明。IR 本身不承诺绝对磁盘路径或通用资源调度，也不成为 Hypha 的提前实现。

## 6. 执行与恢复

先考虑单个 Coop 根目录的一次写操作；不同进程不能同时修改共享入口、状态或 bucket。查询读取已发布的一致状态，不能把中间记录当最终状态。具体锁和发布协议须通过中断测试，不能只凭一次 rename 宣称跨文件事务。

执行先重查本地前提与固定 Manifest 摘要。下载、哈希校验、可独立完成的解压尽量在准备阶段；真正更改 current、入口、环境与管理记录前写恢复日志，记录已完成步骤与原值/归属。只有验证后的完成条件达到，才提交成功状态。

**具体 Scoop 生命周期顺序尚待官方源码调查，本文不给 Hook、Persist、Installer、Shim 排固定顺序。** 特别是 hook 可能依赖最终安装路径，不能默认把所有脚本放到 staging 运行，也不能为了原子切换擅自更改兼容语义。

脚本开始后按实际步骤记录结果，标准输出、标准错误和退出码正确传播；无法判定可逆的外部改动标成需要检查，不自动重跑任意失败脚本。持久化数据可能已被新版本修改，保留旧 EXE 不等于完成数据回滚。

遇到占用不强制结束用户进程；无法安全继续时保持旧版本/入口或进入明确可恢复状态。重启 Coop 后能够报告并处理未完成操作，不能以“上次进程已退出”当作操作成功。

## 7. Git 与解压

Git 已确定使用可由 C++ 调用的库，首选候选 libgit2，见 [ADR-0001](adr/0001-use-embedded-git-library.md)。只为公开 HTTPS 与本地使用范围实现必要操作；不继承未知用户 Git 配置中的凭据、helper 或可执行扩展来绕过首版范围。迁移来源需要识别分支/固定修订，不能一律改成远端默认分支。

增量 fetch 后，索引针对确定 commit 的内容更新；失败时保留可查询的旧发布状态。遇到本地修改、来源不明或不支持的 Git 布局，停止覆盖并给出诊断，不自动 reset/clean。首版不从远端历史查找本机从未安装的旧版本；已有旧目录管理也不意味着其脚本能力自动通过验证。

普通归档已选用固定版本 libarchive 加 zlib/liblzma/zstd/bzip2，静态链接进 `coop.exe`；ZIP、7z、tar 系列及嵌套布局的实际覆盖与边界见[归档生命周期覆盖](archive-support.md)。MSI 产物管理的管理镜像提取使用只读数据库访问（`msi.dll`）与 Windows cabinet 解压 API（`cabinet.dll`），不另引第三方 MSI 读取库；它不等同于执行厂商安装器。Inno Setup 的 `innosetup` 载荷由 root 内单独安装的 innounp helper 解包，Coop 不内嵌也不下载该工具，并在预览和执行前把它作为外部工具需求声明；NSIS 安装器载荷在摘要校验后按内容签名识别，再由 root 内单独安装的 7-Zip helper 按 Scoop `Expand-7zipArchive` 参数解包，同样不内嵌、不下载，普通 7z/ZIP/tar 仍走原生路径；这些也不同于原生理解厂商安装器格式。安装器格式仍按覆盖表区分原生支持、需明确外部工具、已知不支持与未测试；不能因普通归档库支持 7z 就推断可完整替代 7-Zip 对 NSIS/Inno/MSI 等安装器的处理。路径穿越、reparse point、Unicode 和中断处理必须成为测试输入。

HTTP、哈希与进程使用 WinHTTP、Windows CNG、CreateProcessW；JSON、测试框架、普通归档压缩库与构建依赖已固定版本并静态构建。最终优先单个 coop.exe；静态链接体积已核对（只做构建级优化，实测与取舍见 [ADR-0005](adr/0005-binary-size-build-only.md)），许可随附与脚本运行时需求继续核对。

## 8. 验收从完整路径开始

首条路径：**识别既有用户级 Scoop → 预览一个包的接管 → 原地接管 → 本地查询 → 显式更新 bucket → 预览并更新包 → 验证入口与数据 → 卸载并保留数据**。

| 验收 | 可观察证据 |
| --- | --- |
| 无 Git 前置 | 受控测试环境不提供 git.exe，仓库获取与增量刷新成功；进程证据无 git.exe 调用 |
| 本地查询 | 断网时 search/list/info 成功，无 PowerShell 或隐式刷新；不支持执行的包仍可显示 |
| 无重新安装接管 | 接管前后原软件与 persist 路径/内容保留，无安装脚本与产物下载；管理记录正确新增 |
| 渐进接管 | 合格包可管理，不合格包报告原因；系统级、私有/SSH 更新等限制不静默跳过 |
| 预览 | 对比前后安装状态无修改，无安装脚本执行；执行时输入变化会拒绝旧前提或重新规划 |
| 正常更新 | 真实程序可启动、返回预期版本，入口和声明数据正常，旧版本仍在 |
| 下载/校验/解压失败 | 当前版本仍可用，无成功状态误报；残留能识别与清理 |
| 占用/中断/提交失败 | 不强杀程序；恢复日志与实际状态一致，重启可诊断/恢复，不误认成功 |
| 脚本失败 | stdout/stderr/退出码可见；明确可恢复与未知外部副作用，不声称完全撤销 |
| 卸载保护 | 被已知包依赖时阻止；普通卸载保留 persist；彻底删除预览与目标一致 |

在此最高层命令接口验证完整行为；对复杂 IR 转换、计划顺序、路径限制、网络故障和恢复协议再增加必要模块测试。现有仓库无实现和可复用测试，不能填报通过数。

性能保留交接稿目标：version 尽量低于 30ms、缓存 list/info 低于 50ms、索引命中 search 低于 100ms。完整进程测量、冷热与规模数据、实际达成情况、Git 刷新成本和已证实瓶颈的优化见[本地查询与 Git 刷新性能](performance-support.md)。

## 9. 下一阶段与前置证据

以下为建议顺序，不是已下发的实现票，也不由本文自动产生执行授权。

1. **语义与样本**：固定 Scoop/Main/Extras 版本，调查真实生命周期、脚本上下文、shim、persist、依赖、安装记录和解压路径；统计特征并选取 10–20 个真实样本。每个技术结论附源码或运行证据。
2. **项目内构建验证**：复用允许的已有运行时，项目内准备 CMake/MSVC 构建入口，验证 libgit2 的 HTTPS、增量同步、Unicode、静态链接/体积和恢复；不运行 devkit 全局引导脚本。解压候选按相同原则验证。
3. **只读纵向路径**：CLI + 目录读取 + Adapter/IR + 能力诊断，支持本地查询与接管预览；不写现有安装状态。
4. **接管纵向路径**：管理记录、写锁、备份、预条件重查与中断恢复，验证一个真实包原地接管。
5. **原生生命周期路径**：同一个包的安装、更新、入口、persist、卸载、清理及注入失败；不满足证据时不扩覆盖。
6. **脚本兼容路径**：真实样本逐步加入上下文与辅助函数，验证更新和卸载；区分解析成功、计划可生成、生命周期已验证。

语义调查与库可行性是实施细化的前置输入；它们完成后再固定 IR 类型、目录、CMake 依赖与阻塞明确的执行票。正式规格已按用户调用 to-spec 发布到 Issue #2 并标记 ready-for-agent；该标签不代表这些前置验证已经完成，也不产生安装器编码或真实迁移授权。
